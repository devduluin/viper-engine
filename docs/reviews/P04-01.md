## P1: dispatch is admitted after terminal state or cancellation intent

Locations: `src/adapters/persistence/postgres/tool-call-ledger.ts:47,88` and
`src/adapters/persistence/postgres/approval-store.ts:90`.

The run row is locked, but its status/cancelRequestedAt is not checked before creating a new
tool proposal or admitting dispatch. Reproduction through the actual stores:

1. Create/start run, transition to completed with no pending calls.
2. Propose a new call, transition proposed -> ready -> dispatching: every operation succeeds.
3. Stored run remains completed while a new call is dispatching.

A separate running run with durable cancellation intent also admits proposed -> ready -> dispatching.
Atomic approval consumption uses the same unchecked run lock, so it needs the same admission rule.

Expected correction: under the existing run lock, reject new proposals/dispatch/consumption for
terminal/cancel-requested runs. Keep outcome recording/reconciliation available for already
dispatched calls; a blanket prohibition on all terminal-run ledger updates would be incorrect.
Test both ordinary and approval-backed dispatch, including concurrent cancel/admission ordering.

## P1: ordinary ledger transition bypasses approval consumption

Location: `src/adapters/persistence/postgres/tool-call-ledger.ts:88`.

With requiresApproval=true, proposed -> awaiting_approval -> ready -> dispatching all succeed
through ToolCallLedger.transition without creating any approval. Actual database approval count
is zero. The initial proposed -> ready guard only requires visiting awaiting_approval; it does not
prove acceptance, expiry/binding checks or single-use consumption.

Expected correction: make approval-required dispatch reachable only through the atomic
ApprovalStore.consumeForDispatch path (and a separately explicit, evidence-gated retry policy
when implemented). Test direct bypass, expired/rejected/superseded proposals and concurrent consume.
This is a store API invariant, not a claim that HTTP/model input directly exposes these methods.

## P2: unrelated unique violations are masked as a live approval

Location: `src/adapters/persistence/postgres/approval-store.ts:64`.

The catch maps every 23505 to LIVE_EXISTS. Propose an approval with an eventId already present
in run_events: append fails on event uniqueness, the transaction correctly rolls back, but the
returned conflict says a live approval exists. The actual approval count remains zero.
An unrelated duplicate approval primary key is similarly masked, contrary to the store port's
duplicate-create/infrastructure-fault contract.

Expected correction: map only the named approvals_one_live constraint. Rethrow unrelated unique
violations after rollback; test duplicate event ID and approval ID separately.
