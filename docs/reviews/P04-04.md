# P04-04 persistence review and durable-driver integration

Reviewer/integration: Codex. Original persistence: Claude.
Disposition: APPROVED after fixes and actual process-restart verification.

## Persistence findings fixed

- MessageStore used a shared run lock before event append upgraded it. Concurrent writers could
  deadlock while one held the conversation and the other retained the shared run lock. Appends
  now acquire the update lock first, preserving run -> conversation ordering.
- Omitting runId bypassed the terminal-run check for assistant/tool messages. Only user input
  may be appended without a run. Tool results must answer a call from that exact run, not another
  run in the same conversation. Messages are parsed into immutable snapshots before awaited I/O.
- CheckpointReader issued parallel queries on one pg connection (deprecated driver queue).
  Snapshot queries are sequential and ledger/approval reads also have explicit record bounds.

## Required durability added

The persistence half did not store counters, repetition/unknown fingerprints, absolute deadline,
or the execution phase. Separate store commits also left a crash window between a tool outcome
and its result message. Snapshot reads alone did not close these gaps.

- Migration 0007 adds scoped, revisioned runtime_checkpoints. Earlier migrations remain unchanged.
- RunJournal commits commands through the existing reviewed stores in one transaction. It locks
  run and conversation, checks lease/checkpoint revision, and rolls back all earlier commands if
  a later one conflicts. Ledger, result message, events and runtime state share that commit.
- Core exposes serializable budget state, restored counters/reports, decision metadata, per-call
  result messages at report time and a post-correction checkpoint boundary. Default loop behavior
  remains provider-neutral; no SDK/database imports enter the core.
- DurableRunDriver claims, loads the server checkpoint, refreshes authorized tools, runs the core,
  heartbeats, polls cancellation and releases its lease. Worker shutdown/lost lease yields work;
  it does not masquerade as user cancellation.
- Pending model attempts retain their reservation and become failed/unknown on recovery. A tool
  dispatch without a confirmed outcome becomes unknown and ends partial (cancelled if requested).
  It is never sent again. Committed outcomes/final messages resume without duplicate RPCs.
- Input/approval pause retains the same run, budgets and deadline. Authenticated wake invalidates
  the paused lease. Amendments answer the old call and materialize only the new stored proposal;
  current schema, permission, tool version and approval are checked again before dispatch.
- Waiting runs with durable cancellation intent are claimable for cancellation cleanup only.
  Cancellation that wins a transaction restores the last committed state before settling.

## Evidence

- Independent isolated PostgreSQL suite: 73/73 PASS (55 earlier + 18 driver/persistence cases).
- Includes four actual child-process deaths: after fixture effect, after outcome commit, after
  final-message commit and after model-intent reservation. A new worker takes over after expiry.
- Fixture effects are committed DB rows; repeated dispatch would increase their count. Both
  unknown and success recovery preserve the single original effect. No live provider/MCP used.
- Further tests: approval accept/wake, input, amended args, waiting/active cancellation, lease
  loss, heartbeat beyond the original TTL, journal rollback, concurrent append, message origin,
  absolute duration, repetition and a cancellation/intent race.
- Check: 190 unit + 132 contract = 322 PASS. Build/OpenAPI export and architecture limits PASS.
- Explicit review-only settings, viper_it_* DBs on the stopped-afterwards review cluster;
  no .env, application/dev/V4 DB, new dependency or credential access by this task.
