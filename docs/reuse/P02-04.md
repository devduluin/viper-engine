## Intentional behavior changes

1. Trusted transport evidence is an explicit adapter parameter; tool/business body statuses and
   arbitrary message text do not masquerade as HTTP/auth evidence. Matching is exact known
   machine codes, not substrings or suffix routing. Unknown codes remain unknown.
2. HTTP 401/403 take priority over other hints. Explicit OAuth codes then take priority over
   generic HTTP statuses (e.g. invalid_grant with HTTP 400). Other known HTTP statuses precede
   network codes. insufficient_scope maps to permission, not invalid credentials.
3. Payload-code convention is root code or nested error.code up to four error levels. Root known
   code wins within the body. Raw text is preserved but has no authority; only parseable JSON
   objects in text can supply a fallback machine code when structuredContent is absent.
4. Conflicting JSON-text codes remain unknown. StructuredContent, when present, is authoritative
   over text fallback, including an explicit empty object. isError=false/absent means protocol
   success even if business data happens to contain status/code/error-like fields.
5. Complete text/image/audio/resource-link/embedded-resource bodies survive normalization.
   Wire annotations/extras are namespaced under privateMeta.envelope or privateMeta.content;
   reserved normalization metadata cannot collide with arbitrary wire field names.
6. Exactly one text block containing a JSON object may supplement absent structuredContent.
   Original text/media remain intact; privateMeta.normalization records json_text provenance.
   Multiple text blocks and JSON arrays/scalars are not coerced into a structured object.
7. Received isError=true becomes an error outcome. Malformed/unsupported/cyclic/deep input
   becomes unknown, never an empty success. After a transport failure, sent/unknown dispatch
   remains unknown; only an explicit not_sent fact gives error. No automatic retry occurs.
8. A retryable failure is guidance only. Access, reconnect, ownership, approval, schema repair,
   execution certainty and write retry policy remain application/runtime responsibilities.

## Canonical JSON v1

This is a versioned project encoding, not a claim of full RFC 8785/JCS conformance.

- Recursively sort object keys by JavaScript UTF-16 order; preserve array order.
- Encode strings/finite numbers/null/booleans using JSON encoding. Negative zero is encoded 0.
- Preserve string code points; no trimming, case folding or Unicode normalization.
- Reject ill-formed surrogate strings/keys, undefined, symbols, bigint, non-finite numbers,
  functions, cycles, depth >32, custom prototypes, hidden/accessor properties, sparse arrays,
  array subclasses/extra fields and custom iterators. No getter/toJSON coercion is invoked.
- Repeated acyclic references are encoded by value. Null-prototype objects and literal
  __proto__ keys are supported without prototype mutation. Inputs must be transport-parsed
  data, not hostile in-process Proxies. Payload width/byte limits remain caller policy.

Digest bytes: UTF-8 of `viper-fingerprint` + NUL + canonicalJson([domain, version]) + NUL +
canonicalJson(payload), hashed with SHA-256; lowercase full 64-character hex output.
Domains are bounded lowercase ASCII identifiers; versions are bounded explicit identifiers.
Independent Python hashlib vector for domain approval/version v1/payload {a:1} is recorded
in tests so byte encoding changes cannot silently alter old approval snapshots.

A digest is not a MAC/signature/permit. Approval assembly must explicitly include actor/app/
optional tenant/run/connection/server/tool/definitionVersion/final args from trusted server state.
Project TrustedScope into plain scope fields; do not hash its in-process symbol brand.
Persistent lifecycle/expiry/consumption checks and access revalidation belong to P04.
