## Components and interfaces

- `src/agent/policies/limits.ts`: RunLimits, immutable defaults, input validation and typed reasons.
- `policies/budget.ts`: per-invocation counters, atomic proposal reservation, canonical repetition
  keys and uncertain-outcome suppression. Snapshot contains counters, never payloads or credentials.
- `policies/control.ts`: injected epoch clock plus real timer, abort propagation, bounded gateway
  waits and cleanup. Uses adopted P02 withDeadline/assertTimerDuration, not another timeout helper.
- `runtime/stops.ts`: budget/deadline failure or partial if unknown; cancellation remains explicit.
- Runtime/execution handlers integrate those controls while the coordinator stays below 180 lines.
- RunLoopInput adds optional `limits`; RunLoopResult adds frozen `budget`. Existing maxModelCalls
  and per-model-call maxOutputTokens remain host-owned. Direct module paths are the integration API;
  root exports are unchanged because the root dependency policy exposes contracts/bootstrap only.

## Default bounds

| Limit | Default | Counts |
| --- | ---: | --- |
| maxSteps | 32 | Reserved model steps, including failed/interrupted attempts |
| maxToolCalls | 32 | Proposed calls, including rejected/undispatched calls |
| maxDurationMs | 120000 | Real asynchronous gateway wait and injected-clock deadline |
| maxModelOutputBytes | 262144 | UTF-8 JSON bytes of each normalized model result, including usage |
| maxToolOutputBytes | 262144 | UTF-8 JSON bytes of each normalized tool outcome, including private metadata |
| maxTotalOutputBytes | 1048576 | Cumulative received model/tool result bytes |
| maxRepeatedToolCalls | 3 | Same scope/run/connection/server/name/version/canonical arguments |

Limits must be positive safe integers; maxDurationMs cannot exceed Node's 2^31-1 timer range.
Settings, instructions/history and tool bindings are snapshotted. Output cannot reset limits.
Provider-reported output tokens exceeding maxOutputTokens also stop before accepting the decision.
Estimates remain approximate; byte bounds apply even when token usage is unavailable. Media payload
bytes count; there is no claim of a complete media-aware token budget.

## Stop and execution semantics

- A refused proposal batch is not appended, so no pending call IDs are fabricated. A refusal
  after a previous batch preserves complete history and known outcomes.
- Before and after awaited dispatch intent, check cancellation, deadline and uncertain-call key.
  No new gateway invocation follows a stop. After dispatch begins, timeout/abort/fault may leave
  an unknown outcome; it is recorded as unknown, never retried here.
- Unknown calls cannot be repeated under a new ID in this invocation, including the same batch.
  Repetition key uses canonical SHA-256 domain `runtime-call`, version `v1`; not an authority token.
- Output over a limit is omitted with a bounded marker. Known success/error/unknown status remains
  unchanged. Remaining calls receive not-dispatched results so pairing stays complete.
- Budget/deadline stops are failed; any unknown evidence makes them partial. Cancellation is
  cancelled with unknown reports retained. A fluent answer cannot override these states.
- Automatic gateway retries are zero. A retryable flag/prose cannot repeat an external action.
- Model response decisions are parsed again before execution. Duplicate call IDs stay invalid.
- Runtime result counters include observed oversize data; sums saturate safely and stop rather
  than wrapping. Synthetic control feedback is not received provider/tool output and is excluded.

## Durability boundary for P04 / P03-04

- `ToolCallReport.dispatchState` distinguishes `not_sent` and `sent_or_unknown`. A dispatch intent
  may already be persisted before cancellation prevents actual invocation. The durable sink must
  close that dispatching attempt as failed/known_not_applied, not perform the forbidden
  dispatching -> cancelled state transition. Reports before intent can map to ordinary cancellation.
- The core does not detach durable event-sink writes on timeout. Sinks are awaited and must have
  their own bounded I/O/transaction policy. Cancellation is rechecked after they finish. Real timers
  cannot preempt synchronous CPU work or force a remote side effect to roll back.
- Timed-out gateway promises have late resolution/rejection absorbed. Their results cannot append
  to completed runtime history or revive a stopped run. Reconciliation remains the durable driver.
- Counters/uncertain keys are in-memory per invocation. P03-04/P04 checkpoint/resume must restore
  run-wide budgets/ledger facts and refuse completed/unknown re-dispatch across restarts. This task
  does not implement durable resume, consume approvals, or reset budgets safely after restart.
