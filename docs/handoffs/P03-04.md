## API and behavior

`AgentRunSession.start(input, deps, approvalTtlMs?)` returns an ephemeral server controller after
the initial loop stops. `deps.refreshTools(scope)` is required and must be a trusted authorized
catalog lookup. Scope arguments are authenticated server values; no HTTP adapter is implemented.

- `snapshot(scope)`: immutable cumulative result, local command revision and typed pause actions.
- `submitInput(scope, {inputId, expectedRevision, content})`: waiting-for-input only, user role
  constructed by the server. Exact input retry returns original acceptance before stale-revision
  checks; changed content conflicts. Concurrent work returns run_busy, without another model call.
- `decideApproval(scope, {approvalId, expectedRevision, binding, decision})`: accept/reject exact
  stored binding. This does not invoke a tool. Approval revision differs from session revision.
- `resume(scope, sessionRevision)`: only unanswered calls, using new catalog/access checks and
  the original reservations/IDs. Completed/unknown evidence and every counter are retained.
- `reviseProposal(scope, {approvalId, expectedRevision, arguments})`: validates new args, supersedes
  prior acceptance, closes the old call as not-dispatched and creates fresh call/approval IDs.
- `cancel(scope)`: settles paused proposals with paired cancellation results; terminal no-op.
  `requestCancellation(scope)` aborts in-flight work explicitly. Closing a client is not cancellation.

Approval actions include readable final arguments, scope-checked exact tool binding, SHA-256
arguments digest, expiry and status. Digest domain is `approval-arguments`, version `v1`; only
canonical arguments are hashed, with run/call/tool identity separately bound in ApprovalBinding
and owner scope in ApprovalRecord. Digest is not an authorization token.

Current catalog changes supersede approval; expired proposals stay non-executable. Changed deferred
tools expose catalog_changed and require a new plan/run or cancellation. Policy denial overrides
acceptance. A synchronous beforeToolInvoke hook rechecks policy/expiry/binding after the awaited
dispatch intent, immediately before gateway invocation; the MCP gateway still rechecks ownership
and availability. An already consumed approval is never reused for a fresh call.

In-memory consumption precedes the awaited intent event. If expiry/revocation wins that await,
execution returns not_sent feedback. P04 must persist consumption+intent atomically and settle
known_not_applied; it must never reset a consumed approval or claim that the remote action ran.

## Bounds and deterministic outcomes

- Budget/step/model counts, repetition/unknown suppression and history persist across pauses
  within the same controller. Absolute deadline is fixed at start and includes time waiting for
  a human; timers/listeners close while paused. Configure a suitable host duration for interaction.
- Added maxCorrections (default 2): at most two model repair turns after pre-dispatch invalid
  alias/argument feedback. Further failure stops correction_limit with paired history.
- Known MCP failure/unknown still determines failed/partial status independently of fluent text.
  Successful empty/zero/false content is not automatically failure. Simple final-only work uses
  one model call; no mandatory extra planner/verifier/adjudicator was introduced.
- Infrastructure faults poison the controller so an in-memory retry cannot repeat ambiguous
  effects. Unexpected sink failures propagate; durable recovery belongs to P04.

## Contract refinement and durable boundary

- ApprovalView response/event schema now requires concrete final arguments. This is a pre-release
  P01-04 refinement before HTTP implementation, not a shipped API migration; fixtures/export agree.
- Local SessionView revisions are command concurrency tokens, not persisted RunRecord revisions.
  P06 must map through actual store CAS and event transactions; never directly serialize server state.
- AgentRunSession is in-memory, single-process, with no JSON hydration or cross-restart resume.
  It does not wire PostgreSQL approvals or fix persistence findings. P04-02/03/04 own durable
  leases, consumption, idempotency and message/checkpoint serialization/restoration.
- Private core context, stored scope, mutable maps and policies are never client-authoritative input.
  API projection/aggregate input byte/depth/role restrictions remain P06 responsibilities.
