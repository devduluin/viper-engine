## Behavior

- **Claims**:
  - `claimNext(worker, at, leaseMs)` picks the oldest claimable run (`queued`/`running`, unleased
    or expired) with `FOR UPDATE SKIP LOCKED` and raises `lease_fence` by 1. Lease columns are not
    run state: status and revision are unchanged.
  - Waiting and terminal runs are never claimable.
  - The claim returns the owner (to rebuild the trusted scope server-side), the cancel intent, and
    `inFlightToolCalls`.
- **Fencing**: run transitions, tool-call transitions and approval consumption accept a `lease`.
  - It is checked under the run row lock, before any write. Owner, fence and `at < expiresAt`
    must all match.
  - A taken-over worker (old fence) or a lapsed worker (expired, not yet taken over) gets
    `lease_lost` and writes nothing.
  - `renew` and `release` follow the same rule. `release` keeps the fence, so old tokens stay invalid.
- **Crash window**:
  - A call left in `dispatching` is listed as in flight for the next holder.
  - The state machine only allows it to be settled (`unknown`, or an outcome with evidence).
    `dispatching → dispatching` is invalid, and nothing goes back to `ready`, so an uncertain
    remote write is **never re-dispatched automatically**.
  - There is no exactly-once claim.
- **Attempts**:
  - Entering `dispatching` inserts attempt N (dispatch time, worker and fence when leased).
  - Leaving it (`succeeded` / `failed` / `unknown` / `retry_wait`) settles that attempt once.
  - Rows survive run completion. A DB trigger rejects re-settling, identity changes and deletes;
    a unique index allows one open attempt per call.
- **Steps and model calls**: `startStep` enforces gap-free indices (`sequence_conflict`).
  - Model calls start as `pending` and are finished once with outcome, sanitized failure code and
    usage.
  - No prompt, output or provider error text is stored.
- **Idempotency** (owner + operation + key):
  - The first request is `started`. Later ones get `in_progress` until `complete`, then `replay`
    with the stored resource reference.
  - A different payload fingerprint is `idempotency_conflict`. Other actors and tenants have
    independent key spaces.
  - An expired key starts over. `abandon` removes an unfinished claim so a failed request can be
    retried.

## Actual validation

A throwaway PostgreSQL 18 cluster was used (`initdb` in the scratchpad, loopback, stopped
afterwards).
- `npm run test:integration` with `VIPER_TEST_DB_*`: PASS, 34 tests (26 earlier plus 8 new).
- New coverage:
  - five workers race for three runs (overlapping transactions), with distinct claims and fence 1;
  - expiry takeover, with the stale and lapsed writer refused; renew/release by the new holder;
  - the crash window: in flight, then the dead worker is refused, re-dispatch is invalid, and the
    call is reconciled to `unknown`, with the attempt row keeping the dead worker's fence;
  - waiting runs are not claimable; release, then reclaim with fence + 1; fence decrease rejected
    by the trigger;
  - idempotency: replay, conflict, scope isolation, five concurrent firsts giving exactly one
    `started`, abandon, expiry;
  - gap-free steps; model call finished once with usage stored; attempt rows for retry, settle-once,
    no delete, owner-only listing.
- Mutation check: seven breakages, six caught (each restored and verified with `cmp`):
  - caught: fence not raised; ledger ignoring the lease; attempts not recorded; waiting runs
    claimable; fingerprint ignored; expiry ignored;
  - **not caught: removing `SKIP LOCKED`.** This is analyzed, not a gap. PostgreSQL re-checks a
    locked row after the blocking claim commits (EvalPlanQual), skips the now-leased row and
    claims the next one. Correctness holds without it; `SKIP LOCKED` only avoids workers waiting
    on each other (throughput).
- `npm.cmd run check`: PASS (188 unit + 119 contract, 0 violations). `npm.cmd run build`: PASS.
- `npm run db:migrate` on `viper_engine_dev`: `applied [4], current 4`.
