## Behavior

- **Immutable snapshot**:
  - The proposal stores the exact final arguments and the tool definition shown to the approver
    (title/description/input schema/annotation hints), next to the binding (run, call,
    connection, server, name, definition version, digest).
  - `propose` and `revise` verify `createFingerprint(arguments, APPROVAL_ARGUMENTS_DIGEST) === digest`,
    so the stored arguments cannot differ from what dispatch is bound to.
  - A DB trigger makes binding and snapshot immutable.
- **Decisions**:
  - Only the owner's trusted scope can decide (others get `not_found`). `decided_by` comes from that
    authenticated scope and is never derived from model or tool text.
  - The DB requires `decided_by` for accepted/rejected/consumed, and it is written once.
  - Stale revisions → `revision_conflict`; a second decision → `invalid_transition`.
- **Revise (parameter amendment)**, in one transaction:
  1. CAS on the old approval (pending, accepted or expired).
  2. Admission, digest-vs-arguments check, connection access.
  3. The old call → `rejected` (or `cancelled` if it was `ready`).
  4. Insert the amended call (same tool and definition version, new ID/arguments/digest,
     `awaiting_approval`) and its pending approval (same snapshot).
  5. The old approval → `superseded` with `superseded_by`.
  The old proposal can never be consumed afterwards.
- **Revoked access**: `propose`, `revise` and `consumeForDispatch` recheck under lock that the bound
  connection still belongs to the caller, is on the same server, and is `ready`. Otherwise the
  result is `access_revoked`, and the approval and call stay unchanged (nothing dispatches).
- **Expiry**: `expireDue(at, limit)` expires pending/accepted proposals at or past `expires_at`
  (`FOR UPDATE SKIP LOCKED`, so it never waits behind a decision). Accept and consume already
  refuse expired proposals.
