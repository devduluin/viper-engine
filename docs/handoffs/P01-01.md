## Decisions and invariants

- IDs are exact opaque strings, not UUID-only. No trim/case normalization; empty, whitespace,
  control/format characters, nonstrings and values over 256 characters are rejected.
- AuthenticatedIdentity must originate from a server auth/configuration adapter. The scope
  factory validates shape/IDs and snapshots authority; it does not authenticate request JSON.
- TrustedScope has an in-process symbol marker and is immutable. JSON roundtripping loses
  authority; restored data must be checked/reissued from the trusted authentication boundary.
- Payload claims can confirm but cannot overwrite actor/app/tenant. Tenant absence remains
  distinct from any tenant value. Cross-actor/app/tenant access checks fail.
- Clock and ID ports construct no clock/generator; uniqueness and actual time are adapter duties.
- Text/JSON and image/audio sources are provider-neutral. Media may be inline base64 or a URI
  reference. Parsing neither fetches URI content nor decodes or authorizes media.
- Decoders return frozen snapshots, including nested JSON arguments/data and content arrays.
- JSON is strict plain data: reject cycles, depth over 32, non-finite numbers, undefined,
  functions, bigint, custom object prototypes, symbols, hidden fields, accessors, sparse arrays,
  extra array fields/subclasses and custom iterators. No getter/iterator/toJSON execution is used
  to obtain plain data. Validation assumes transport-parsed values, not hostile in-process Proxies.
- Tool outcomes preserve `success`, `error`, `unknown`; empty tool content is allowed.
- History rejects duplicate message/call IDs, orphan/future/duplicate results. Parallel results
  can complete out of order; no provider-specific role alternation is imposed.
- Pending tool proposals are valid for pause/approval. Before a model request requiring complete
  history, set `allowPendingToolCalls: false` to reject unresolved calls.

## Authority and scope limitations

Normalized message validation checks shape/correlation, not whether a client may insert a
system/assistant/tool message. The future application/auth ingress must assign trusted roles,
look up conversation/run ownership and prevent client forgery of assistant/tool execution evidence.
Typed `assertMessageHistory` assumes already-decoded Message values; use `parseMessageHistory`
for untrusted data. Tool names/arguments still require catalog access/schema/policy checks later.
This task does not implement provider conversion, payload budgets, authentication or persistence.
