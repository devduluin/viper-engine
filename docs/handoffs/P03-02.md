## Loop behavior

`model -> plan calls (resolve, validate, policy) -> dispatch -> normalized results -> model`,
until a final answer, a pause, a failure or cancellation.

- **Pairing**: each step appends the assistant message, then exactly one tool result per call in
  model order. Undispatched calls (rejected/cancelled) still get an `error` result with a
  `not_dispatched` marker, so history stays valid for the next model request.
- **No routing**: tools are found by exact alias only (`Lookup` does not match `lookup`). No
  keyword, intent or tool-slug logic exists in the runtime.
- **Validation before dispatch**:
  - unknown alias -> `not_found`;
  - schema failure from the injected validator -> `invalid_value` (+ `field`);
  - policy `reject` -> `permission`.
  The model receives these as error results and can correct itself in the next step.
- **Approval**: if policy returns `requires_approval` for any call in a batch, nothing in that batch is
  dispatched. Calls are reported `awaiting_approval`/`deferred`, rejections are still answered,
  and the run stops `waiting_for_approval`. Proposal/consumption is P03-04/P04-03.
- **Dispatch intent first**: `tool_call_dispatching` is emitted and awaited before `callTool`.
  If the sink throws, nothing is dispatched and the loop rejects. P04 sinks persist here.
- **Unknown outcome**: a gateway throw or malformed reply after the intent becomes
  `unknown` with a generic message (the raw error text is not forwarded). It is never retried here.
- **Terminal status from evidence** (`outcome.ts`), not from the answer text:
  - any `unknown` -> `partial`;
  - failures with successes -> `partial`;
  - only failures -> `failed` (VE-005);
  - otherwise `completed`.
  Pre-dispatch rejections carry no side-effect evidence and do not downgrade a corrected run.
- **Other stops**:
  - `needs_input` -> `waiting_for_input` with the question appended as assistant text;
  - model `ok:false` -> `failed`/`model_failure`;
  - a tool call ID reused from history -> `failed`/`invalid_model_response`;
  - `maxModelCalls` reached -> `failed`/`model_call_limit`;
  - `deadlineAt` passed -> `failed`/`deadline_exceeded`.
- **Cancellation**: the signal is checked before every model call and before every dispatch, and
  passed to the gateways. Remaining calls are answered as `cancelled`; an abort that interrupts the
  model call stops as `cancelled`. Mid-dispatch abort is still recorded as that call's outcome.
- **Events** (awaited, frozen, in order): `model_call_started`, `model_call_finished` (with usage),
  `message_appended`, `tool_call_dispatching`, `tool_call_reported`, `run_stopped`.
- **Private data**: `privateMeta` and binary resource bodies are never forwarded to the model.

The loop keeps state in memory per invocation and returns the appended messages, tool call
reports and model call count. Persisting history/ledger from events is P04-04.

## Not covered (by design; later tasks)

- VE-009 repetition guard, step/tool/time/output budgets, retry policy: **P03-03**. Only a hard
  `maxModelCalls` ceiling and `deadlineAt` exist here, so the loop cannot run forever.
- Approval proposals, resume after input/approval, bounded correction rules: **P03-04**.
- Parallel dispatch of independent calls: calls run sequentially; a policy-gated parallel
  scheduler can replace the loop in `executeCalls` without changing the coordinator.
- Durable ledger/checkpoints driven by the event sink: **P04-02/P04-04**. Tool aliasing and
  namespacing from discovery: **P05-02**. A production JSON Schema validator adapter is wired in
  bootstrap (the agent layer does not depend on a schema library).
- VE-006/VE-007 are application-selected resource/prompt reads, not runtime loop behavior.
