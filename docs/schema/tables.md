# Schema tables: `viper_engine`

Logical PostgreSQL blueprint for P04-01. Decisions are in [ADR-0001](ADR-0001-fresh-schema.md)
and state rules in [state transitions](state-transitions.md). This document is a specification;
migrations live in `src/adapters/persistence/postgres/migrations/` (P04-01). Physical choices made
there are listed under "P04-01 physical decisions" below.

## Conventions

- IDs are `text`, opaque, `CHECK (length(id) BETWEEN 1 AND 256)`, generated by the server.
- Owner columns on every scoped table: `actor_id text NOT NULL`, `app_id text NOT NULL`,
  `tenant_key text NOT NULL` (`''` means a tenant-less deployment). Abbreviated as **owner** below.
- Timestamps are `timestamptz` in UTC. `revision bigint NOT NULL CHECK (revision >= 1)`.
- Status columns use `CHECK (status IN (...))`, mirrored from the contract unions.
- Parents expose `UNIQUE (id, actor_id, app_id, tenant_key)`, and children reference that tuple,
  so a child can never belong to another owner than its parent.
- JSONB columns hold validated, versioned, size-bounded documents (`CHECK (pg_column_size(x) <= limit)`).
  Large payloads use references.

## Core run state

### `conversations`

| Column | Notes |
| --- | --- |
| `id` PK, owner, `title text NULL` | Title optional, bounded length |
| `revision`, `created_at`, `updated_at` | CAS on revision |

Index `(actor_id, app_id, tenant_key, updated_at DESC)` for listing.

### `messages`

| Column | Notes |
| --- | --- |
| `id` PK, owner, `conversation_id` | FK to conversations with owner tuple |
| `run_id NULL` | FK to runs with owner tuple when produced by a run |
| `position bigint` | `UNIQUE (conversation_id, position)`, gives a stable order |
| `role` | `CHECK IN ('system','user','assistant','tool')` |

## Execution ledger

### `tool_calls`

| Column | Notes |
| --- | --- |
| `run_id`, `id`, owner, `step_id` | PK `(run_id, id)`; `step_id` is correlation only until P04-04 persists steps |
| `status` | Tool-call statuses from the contract |
| `revision`, `attempts int NOT NULL DEFAULT 0` | `attempts` only increases |
| `connection_id`, `server_id`, `tool_name`, `definition_version` | Exact `McpToolRef` |
| `schema_snapshot jsonb NULL` | Input schema used for validation; optional audit copy |
| `arguments jsonb NULL`, `arguments_digest char(64)` | The digest is the binding; arguments are an optional audit copy |
| `requires_approval boolean` | Set by policy at proposal time |
| `outcome jsonb NULL`, `evidence jsonb NULL` | Bounded normalized outcome and evidence reference |
| `created_at`, `updated_at` | |

Index `(run_id, status)` lets the settlement check read every call of a run in one transaction.

### `tool_call_attempts` (P04-02, migration 0004)

PK `(run_id, tool_call_id, attempt)`, plus `worker_id`/`lease_fence` (when leased), `dispatched_at`,
`settled_at NULL`, `result_kind`; settle-once and no-delete triggers; one open attempt per call
and `evidence jsonb`. The row is inserted with the `dispatching` transition and is never deleted
by run completion.

### `approvals`

| Column | Notes |
| --- | --- |
| `id` PK, owner, `run_id`, `tool_call_id` | FK `(run_id, tool_call_id)` to tool_calls with owner tuple |
| `connection_id`, `server_id`, `tool_name`, `definition_version`, `arguments_digest` | Immutable binding |
| `status`, `revision` | Approval statuses from the contract |
| `expires_at`, `decided_at NULL`, `consumed_at NULL` | |
| `created_at`, `updated_at` | |

Partial unique index `(run_id, tool_call_id) WHERE status IN ('pending','accepted')` allows only
one live approval per call. A trigger or the repository rejects updates to binding columns.

### `run_events`

| Column | Notes |
| --- | --- |
| `run_id`, `sequence bigint`, owner, `conversation_id` | PK `(run_id, sequence)`, `CHECK (sequence >= 1)` |
| `event_id` UNIQUE, `type` | Event types from the contract |
| `step_id`, `model_call_id`, `tool_call_id` NULL | Correlation |
| `occurred_at`, `payload jsonb` | Bounded public-safe payload |

Index `(occurred_at)` serves retention (default 7 days). Inserts share the transaction with the state change.

### `request_idempotency`

PK `(actor_id, app_id, tenant_key, operation, idempotency_key)` with `payload_fingerprint char(64)`,
`resource_ref`, `created_at` and `expires_at` (default 24h). If the same key arrives with a
different fingerprint, the result is `409 IDEMPOTENCY_CONFLICT`.

## Deliberately absent

These are not created: `tools`, `knowledges`, `skills`, `intents`, intent examples/mappings,
embedding/vector tables, device or desktop tables, or any V4 foreign keys. Later phases
(P07 notes, P06 jobs/outbox) add their own migrations.

## `runtime_checkpoints` (P04-04, migration 0007)

- run_id PK with owner columns and composite run FK; all access checks the owning run.
- revision starts at 1 and advances by exactly one; run/lease lock plus checkpoint CAS admits writes.
- state JSONB is a versioned application snapshot bounded to 2 MiB: model/ceilings/deadline,
  budget counters and repetition/unknown fingerprints, reports, phase and current audit identities.
- Written by RunJournal in the same transaction as ledger, messages and events; not a separate
  best-effort save after an external action. Never hydrate from client-submitted JSON.
- Source migration checksums 0001..0006 are preserved. Deployment must explicitly apply 0007.

## P04-01 physical decisions

P06-02 migration 0010 updates the append guard to preserve run high-water sequence after a
retained event prefix (including all rows) is pruned. No new table: 16 engine tables plus ledger.
Public payloads hydrate only immutable same-run facts; [stream guide](../event-stream.md) covers
retention lookback/gaps/snapshot fallback. Physical cleanup jobs remain P08.

P06-03 migration 0009 adds `run_deliveries`: owner FK, failed lease fence, cumulative failure
count, safe failure code and database-time available_at. Written under a live failed holder's
lease before release; claim SQL skips deferred work except cancellation. Current total:
16 engine tables plus migration ledger. See [worker guide](../worker-host.md).

P06-01 migration 0008 adds `run_instructions` and `input_receipts`: private prepared system
messages per run, and dedup fingerprint/original acceptance per run/inputId. Both have owner
composite FKs, bounded JSONB and immutable-update guards. Commands commit these atomically
with reviewed run/message/idempotency stores. Total: 15 engine tables plus migration ledger.
See [HTTP guide](../http-api.md); earlier migration/checksum files are unchanged.

- The runner creates `viper_engine` and `viper_engine.schema_migrations` (version, checksum).
- Domains `entity_id`, `tenant_key`, `revision`, `sha256_hex` carry the shared checks.
- Triggers enforce: revision steps of exactly +1; immutable owner columns; immutable tool call
  identity/arguments/approval flag; non-decreasing `attempts`; immutable approval binding;
  gap-free append-only `run_events`; append-only `messages`.
- One tool result per call is unique per conversation (history pairing is conversation-wide),
  stronger than per run, and also covers results stored without `run_id`.
- `tool_calls` references the caller's own connection and its exact server; `approvals`
  references the full binding tuple of its tool call, so a mismatched binding cannot be stored.
- `conversations.next_message_position` allocates `messages.position` (from 1) inside the CAS write.
- `run_steps.step_index` starts at 1; `model_calls.outcome` is `pending|succeeded|failed|cancelled`
  and `failed` requires `failure_code`.
- JSONB size limits: content/arguments/outcome 256 KiB, schema snapshot 128 KiB, event payload
  and server config 64 KiB, capabilities/evidence 16 KiB, budget 8 KiB.
- Migration 0003 names the caller-connection FK `tool_calls_caller_connection_fk`; repositories
  map only named constraints (this one and `approvals_one_live`) to conflicts.
- Repositories also enforce admission (no new tool work on terminal/cancel-requested runs) and
  approval-only dispatch for `requires_approval` calls.
- Not enforced in SQL (repository responsibility): status transition graph, settlement, expiry,
  and private-server ownership (`mcp_servers.owner_actor_id`).

## Reviewed memory extensions

Migration0011 adds explicit user-source notes and metadata-only note changes; migration0012 adds
append-only outcome_feedback, immutable memory_proposals and memory_proposal_changes. Current
schema:21 engine tables plus migration ledger. Composite owner/source FKs, exact user confirmation,
revision transitions and atomic feedback invalidation protect proposal promotion. Read
[scoped recall](../scoped-recall.md) and [outcome proposals](../outcome-proposals.md) for full semantics.
